## 3. 系统「使文本更大」（`TextScaleFactor`）——能改、能验、已还原

### 3.1 先读当前值

```
原始 TextScaleFactor = []（没设过 = 系统默认 100%）
```

**注意区分两件事**（这一条最容易读混）：
- **「使文本更大」** = `HKCU\Software\Microsoft\Accessibility\TextScaleFactor`（**本条验的是它**）；
- **显示缩放** = DPI（125% 会让**整屏**变小）——**那个 `-18` 验过**：这台机器的显示适配器
  **不支持**调（DisplayConfig GET/SET 都返 `rc=87`），**改不了**。

**实测结论：`TextScaleFactor` 这台机器能改、而且生效不用重新登录** ——
设下去之后同一个会话里新启动的应用立刻按新比例渲染（下面尺寸变化就是证据）。

### 3.2 100% / 125% / 150% 各跑一轮首页（原始输出）

### 3.3 「设置真的生效了吗」——用尺寸变化证明，不是靠窗口尺寸推

```
=== 设置真的生效了吗（同一段文字的尺寸随比例长）===
  TextScaleFactor=100%：标题高=33逻辑  正文宽=288
  TextScaleFactor=125%：标题高=41逻辑  正文宽=360
  TextScaleFactor=150%：标题高=49逻辑  正文宽=432
```

**判据与结论**：
- **文字确实随比例变大** ✓（33 → 41 → 49 逻辑高，约 1.25× / 1.5×）。
- **三个档位都没有横向裁切** ✓（`横向溢出=0`；标题宽 768→1070，最宽时右边界 1210 < 客户区右 1272）。
- **`客户区内=False` 那两行（125%）是纵向的**，不是被裁：页面本来就可滚动，而**滚动位置
  会跨启动保留**（WebView2 档案里存着），所以有时量到标题在视口上方（`top` 为负）。
  脚本已经**先滚到顶再量**（`Scroll-ToTop`），判据只看**横向**；
  纵向只作事实记录（见 §7 坑 3 —— 这一条一开始把我坑出了假红）。

### 4.3 读法（重要）

- **两组数字逐项完全相同** —— 这不是"巧合"，是**产品不读系统主题**：界面底色写死在

  **没有业务命中**；只有 `VirtualList.tsx` 读 `prefers-reduced-motion`，那是动画偏好，不是主题）。
- **所以「暗色/亮色切换后对比度是否还够」这个问法，在本产品上不成立** ✗ ——
  系统主题**不影响**这个界面。这**不是缺陷**（产品只有深色界面这一个形态），
  但**必须如实写清**：我没能"验出主题带来的差别"，因为**差别本来就不存在**。
- **量到的对比度**（像素采样，取元素矩形内最暗/最亮两色的 WCAG 比值）：
  - 正文类（`点一张卡片`、`历史`、`隐私`）≈ **7.83**

  > 字确实分得开"）。真要判 WCAG，得在**计算样式**上算（那需要 DOM 访问，不是 UIA 能给的），

## 5. 我没能验证什么（如实列，不写成「通过」）

1. **多屏 / 第二种显示配置：验不了** ✗ —— 这台机器**只有 1 个显示设备**（§2）。
   所以「副屏在主屏左边/上面时版面怎样」「两屏 DPI 不同时窗口跟着谁」这些**一条都没验**。
2. **系统主题这条，验不出"切换带来的差别"** ✗ —— 不是没跑，是**产品不响应系统主题**（§4.3）。
   换句话说：我验的是"切换系统主题后**界面不变**"，**不是**"亮色主题下对比度够"。
   「亮色界面」这个形态**这个产品根本没有** —— 要验它得先有那个形态。
3. **真 125% / 150% **显示缩放**（DPI）下的渲染** ✗ —— 与 `-18` 同样的原因：这台机器的显示适配器
   不支持调（`rc=87`），**改不了**。本轮的 125%/150% 是**「使文本更大」**，**不是**显示缩放；
   两者都会让字变大，但**作用机制不同**（前者只放大字体，后者放大整个 UI）—— 别读混。
4. **对比度不是 WCAG 判定** ✗ —— §4.3 说明：像素采样是近似，没设门槛。要判 WCAG 得从计算样式算
   或用专门扫描器，**本轮没做**。
5. **向导的「检查电脑」那一步没验失败分支** ✗ —— 这台机器组件齐全，所以走到的是"已经就绪"
   那一支；"缺组件时向导怎么显示"（`WIZARD_HEALTH` 那几条文案）**没验**。
6. **没有验真机上的鼠标点击**：版面量的是 UIA 矩形 + 滚轮 + `invoke`（UIA 的调用，不是真鼠标
   点像素坐标）。**"她用手指/鼠标点在那个像素上灵不灵"这一层没验** ✗（`-19` 里同样记过这一条）。
7. **每场各跑一遍（个别跑了多次）** ✗ —— `wizard` **2** 次（第 1 次判据写错）、`screens` **1** 次、
   `textscale` **5** 次（前 4 次在修脚本/环境抖动，最后一次 `textscale5` 有效）、
   `theme` **6** 次（前 4 次在修脚本 + 环境抖动，后两次 `theme5`/`theme6` 有效且一致）。
   要达到"各 3 次结论一致"的硬度，得再跑。

## 7. 踩过的坑（都是「看起来像产品坏了、其实是工具/环境」）

1. **残留的 WebView2 渲染进程会占住应用档案**：上一次跑被中断后，`msedgewebview2.exe` 还挂着
   `%LOCALAPPDATA%\dev.cante.gui`，于是下一次启动**直接 `exit=-1`**，看起来像"应用起不来" ✗。
   **修法**：启动前清掉**属于这个应用**的 WebView 进程（按命令行里含 `dev.cante.gui` 过滤，
   不动她正常的 Edge）。
2. **等值匹配中文标题会漏**：首屏标题渲染成「**你好，**需要我帮你做什么**？**」，
   而脚本一开始按等值找「需要我帮你做什么」→ 找不到 → 把"首页没渲染"误报成失败 ✗。
   **修法**：所有找 UI 中文的地方改成**包含**匹配。
3. **滚动位置跨启动保留 → 纵向坐标会骗人**：应用档案里存着页面滚动位置，于是标题有时量到
   `top=-171`（在视口上方）—— 那是"页面被滚下去了"，**不是文字被裁** ✗。
   **修法**：量之前**先滚到顶**（`Scroll-ToTop`），判据只看**横向溢出**，纵向只作事实记录。
4. **量之前要重新取客户区**：窗口位置会被"窗口状态"插件恢复，启动时取的客户区可能过期，
   于是元素的屏幕坐标看起来"在客户区外"（`top=-477`）✗。**修法**：每次量元素前重新取一次。
5. **UIA 对 WebView2 报的颜色是 `(0,0,0)`**：不能拿它当对比度证据（§4.4）。**改用像素采样**。
6. **把"验不了"与"不符合"分开**：`screens` 那条用**独立的退出码语义**（2 = 验不了），
   否则报告会把"这台机器只有一个屏"写成"产品有问题" ✗（任务点名要求区分）。
