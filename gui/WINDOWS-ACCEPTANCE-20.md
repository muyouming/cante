## 1. 改了什么（两件事）

### 1.1 去重逻辑：改成**优先 runtimeId**（任务第 1 条）

原实现（`El-Identity`）是 `类型 + 名字 + 矩形左上角`。任务说它「按名字去重」——**这点要更正**：
我核对过 `origin/main` 上的脚本，它**当时已经**带了矩形（`WINDOWS-ACCEPTANCE-19.md` §2 也写了这条）。
但它**仍然不够**，我实测出一个更麻烦的事实：

```
结果面板 47 行同名按钮，Tab 逐个走过它们时列表会在滚动 ——
实测这 47 个按钮只有 5 个不同的矩形左上角（y 值在 410/493/638/695/721/743 之间反复复用）。
→ (名字 + 矩形) 会把 47 个不同行折叠成 5 个身份 ✗
```

所以我把身份改成 **优先用 `GetRuntimeId()`**（UIA 给每个元素的分身证：同一元素稳定、不同元素不同、
不受滚动影响），拿不到才退回 `类型|名字|矩形`。并**把这条判据靠什么成立打进输出**：

```
（身份来源：runtimeId 可用 97 次 / 退回矩形 0 次）
```

**这一轮本机 runtimeId 完全可用**（97/97），所以「Tab 不卡、不重复」这条判据站得住。
如果哪天在别的机器上 runtimeId 不可用，输出会显示「退回矩形 N 次」，报告里就能如实说清。

### 1.2 新判据：`distinct-button-names`（任务第 2 条）

在 `Judge-Visited` 里加了：枚举 Tab **真到得了**的按钮，统计**不同名字的个数**，
打印 `可 Tab 按钮 N 个 / 不同名字 M 个`，并把名字**按出现次数**列出来。
当 **M < N/4** 时判据**红**（不是只"显眼"，见 §3 的取舍说明）。

## 2. 基线是怎么跑出来的（可重复）

**难点**：面板要有行才有按钮。上一轮那 47 行是**那台机器攒的真实历史**，不可重复
（档案一清就空）。所以本轮加了一个**夹具**：显式铺固定行数，修复前/修复后两次跑的是同一个面板。

```powershell

powershell -NoProfile -ExecutionPolicy Bypass -File gui\scripts\windows\a11y-uia.ps1 `
  -Scenario results -WorkDir <工作目录> -Exe <现构建的 cante-gui.exe>

# 2) 还原（跑之前原本没有 runs.json，就删掉；有就放回备份）
powershell -NoProfile -ExecutionPolicy Bypass -File gui\scripts\windows\seed-result-rows.ps1 `
  -Mode restore -WorkDir <工作目录>
```

**跑了四次，N/M 都是 95/3**（同一条命令、同一份夹具；第四次是修完全部工具问题后的终态）：

| 次 | N | M | Tab 一圈 | 污染？ |
| --- | --- | --- | --- | --- |
| 第 1 次 | 95 | 3 | 96 步回到起点 | 无（`no-focus-steal` 没触发） |
| 第 2 次 | 95 | 3 | 96 步回到起点 | 无 |
| 第 3 次（final） | 95 | 3 | 96 步回到起点 | 无 |
| 第 4 次（run4，工具全修后） | 95 | 3 | 96 步回到起点 | 无 |

> **为什么是 95 而不是 94（47×2）**：面板每行两个按钮，但 Tab 只走到**它真能走到**的那些；
> 95 = 47 + 47 + 1（「回到首页」）。搜索框是 `Edit`，不计入按钮 N。

## 5. 顺手修掉的五个**工具**问题（不碰产品代码）

这五个都是**这一轮实跑踩到的**，会让人**误判产品**，所以一并修了：

1. **去重按 runtimeId**（§1.1）—— 名字+矩形也会被滚动折叠（47→5）。
2. **杀进程要连 WebView2 子进程一起杀，并等它退干净。**
   实测：`cante-gui.exe` 被强杀后，它的 `msedgewebview2.exe` 子进程继续持有用户数据目录几秒，
   这时马上启一个新的，**新进程立刻退出（exit 1）**、日志里什么都没有 ——
   看起来像「应用起不来」，其实是上次没死干净。修法：`Clear-StaleApp` 里循环收掉 webview 子进程；
   启动失败时**清一遍再试一次**，并在报告里写明那是第二次尝试。
3. **拿不到前台就快速失败，不再硬等**（这也是“命令别超 10 分钟”的直接原因）。
   实测：机器上有个**提权的「任务管理器」窗口**（我杀不掉，`Stop-Process` 报 Access is denied）
   会抢前台，而 `Ensure-Foreground` 每次重试 12×200ms ≈ 2.4s；220 步 × 2.4s ≈ **8.8 分钟**，
   直接顶到我 9 分钟的上限（**第一次跑就是这样超时的** ✗）。
   修法：`Press-Tab` 连续 3 次拿不到前台就抛异常、`Tab-Round` 就地收手、
   上层记为**环境问题**（“读数不可信”），**不**把它误判成「Tab 卡住了」。
   （那个任务管理器窗口已经由隔壁工作树的 peer 提权关掉了 —— 但这道改正仍然该留：
   下次再有提权窗口冒出来，不能让一条 8.8 分钟的命令把整轮堵死。）
4. **日志会丢掉一部分输出（最阴的一个，修它的时候差点又踩回坑里）** ✗：
   `Say` 用的是 `Write-Output`，而当函数被**赋值调用**时（`$round = Tab-Round …`、
   `$elements = Dump-And-Judge …`），它的输出**全被吞进变量**，控制台一个字都不打 ✗。
   后果：**报告文件是全的，而控制台/日志里看不到 Tab 的每一步与元素清单** ——
   看日志的人会以为那几个函数没跑。改成 `Write-Host`（它不进管道）。
   > 但改完立刻就暴露了一个**本来就被掩盖着**的 PS 5.1 坑：
   > `$round.elements` 是 `List[object]`，而 **`@(<List[object]>)` 在 PS 5.1 会抛
   > 「参数类型不匹配」**（`$list.Count` / `[array]$list` 都正常，就 `@()` 不行）。
   > 之前之所以没炸，是因为 `Write-Output` 的污染把 `$visited` 变成了**数组**、
   > 顺手替 `@()` 遮了一下 —— 我把日志修好，就把它翻出来了（`Judge-Visited` 里
   > `@($round.elements)` 改成显式枚举）。**修完两次都验了**：控制台 95 行 Tab 步骤、
   > `visited-results.json` 正常写出、N/M 仍是 95/3。
5. **夹具的备份/记号放在 `runs.json` 旁边，不放在 WorkDir 里** ✗：
   `runs.json` 是**全局一个**，而 WorkDir 每次跑一个。记号跟着 WorkDir 走的话，
   从**另一个** WorkDir 调 `-Mode restore` 就找不到它，“还原”会变成“不动它”——
   于是那 47 条**假记录就留在她面板里** ✗（我清机器时差点就这么留下了）。
   改成放在 `file-safety\runs.json.seed-{backup,marker}`；并实测了**跨 WorkDir 还原能成功**。
