## 2. 「读屏会怎么念」清单（三个界面，逐条）

### 怎么取的、为什么是这一层

- **起点 = 应用的 `Document` 元素**，不是窗口根 —— 天然排除窗口按钮与 **Edge 自己的 chrome**
  （地址栏、翻译、收藏）——那些不是 Cante 的界面。
- **顺序 = UIA 树序（深度优先）= 文档顺序 = 读屏朗读顺序。**
- **视图 = `ControlView`**（`TreeWalker.ControlViewWalker`）。**这是本报告与上一版最大的差别**：
  UIA 有三个视图 —— `RawView`（一切节点）/ `ControlView`（控件）/ `ContentView`（内容），
  **读屏念的是后两个**。上一版走 `RawView`，把 `IsControlElement=False` 的布局节点也算了进去（§3）。
- 每条写 **`控件类型` + `名字`**，读屏念的就是这两样；标题另标 `[标题N级]`，可聚焦标 `[可Tab]`。
- 名字为空的**结构容器**（`List`）也记，因为读屏会念「**列表，N 个项目**」。

## 3. 一条方法纠正（本报告最独立的价值）：读屏走 `ControlView`，不是 `RawView`

**上一版（`narrate-script.ps1`）走的是 `RawView`**，于是算出一批"会被念的东西"，
其中至少两条是**假象**。我把同一棵树的三个视图对照过（原始输出）：

```
RawView   节点（有名字/标题）= 146
ControlView 节点（有名字/标题）= 72
（RawView 里 isControl=False 的节点数 = 74）
```

**假象一：同一个标题不是念两遍**

```
名字在 RawView 里出现多次的，在 ControlView 里出现几次：
  「你好，需要我帮你做什么？」 RawView=2 ControlView=1
  「我做的结果」             RawView=2 ControlView=1
  「还有别的事？」           RawView=2 ControlView=1
  「表格」                   RawView=2 ControlView=1
  「文件」                   RawView=2 ControlView=1
  「微信」                   RawView=2 ControlView=1
  「文书」                   RawView=2 ControlView=1
  「资料」                   RawView=2 ControlView=1
```

那两个同名节点，一个是**真标题**，另一个是它**下面紧邻的 `IsControlElement=False` 的布局节点**
（逐字，原始输出）：

```
view : Raw
depth: 5   kind: Text   name: 我做的结果   heading: 2   isControl: True   isContent: True
view : Raw
depth: 6   kind: Text   name: 我做的结果   heading:      isControl: False  isContent: False
--- ControlView ---
view : Control
depth: 2   kind: Text   name: 我做的结果   heading: 2   isControl: True   isContent: True
```

**读屏不念 `IsControlElement=False` 的节点** —— 所以「标题念两遍」是**遍历视图的产物**，
**不是产品缺陷**。上一版把它列进"刺耳项"，**这一条要撤**。

**假象二：确认页步骤条不是三条碎 Text**

上一版把步骤条读成 `1` / `选文件` / `—` 三条（RawView 里那三条 `isControl=False`）。
**ControlView 里只有 4 个 `ListItem`**：`1选文件—` / `2说需求—` / `3确认—` / `4结果`。

> **这条纠正与另一条分支的结论一致**：那份用 ETW 抓 `SpokenText` 的报告，
> 也把「按 UIA 树算出来会念的 100 字 `ListItem`」判为高估（`ListItem` 不可 Tab，键盘走不到）。
> 两条路从不同角度得到同一结论：**"树里有什么"≠"读屏念什么"**。

## 4. 最刺耳的 3 条（都有实测秒数）

> 秒数 = 把字符串交给**这台机器上的中文语音**（`Microsoft Huihui Desktop`，zh-CN）
> 合成 WAV、**读 WAV 头**算出来的（22050Hz/16bit/mono）。**不是按字数估的**，也**不是**从音频设备抓的
> （这台机器没有声卡，§1.5）。字符串**逐字**取自真机的 UIA `ControlView` 输出。
>
> ②③ 的句子在另一条分支的 **ETW `SpokenText`** 里**确实出现过**（我拉回本机核对过），
> 所以是"读屏真的会念"；① 是 UIA 层的句子，**ETW 未单独抓到**（如实标）。

### ① 首页卡片的按钮名字 = 「卡名 + 句号 + 例子」→ **念 10.7 秒/张**

```
「把几张表合成一张（自动去掉重复行）。把这三个月的销售表合成一张，重复的记录只留一条」
   字数 = 41   念出来 = 10.7 秒
对照组（只念卡名，不含例子）：
「把几张表合成一张（自动去掉重复行）」
   字数 = 17   念出来 = 4.8 秒
```

**为什么刺耳**：她要在一屏 **33 张卡**里挑一张。每张卡的名字里都塞着一个**完整的举例句子**，
而且中间只有一个**句号**连着——读屏听完**一张卡 10.7 秒**，33 张光是听卡片就**接近 6 分钟**，
而她本来只想知道"这张卡是干什么的"。（去掉例子只要 4.8 秒。）

### ② 结果面板每一行：两个按钮各念一遍文件名 → 一行 **12.3 秒**

```
「打开 结果_挑出华东区-1.xlsx」              字数=18  念出来=5.5 秒
「打开 结果_挑出华东区-1.xlsx 所在的文件夹」  字数=25  念出来=6.8 秒
```

**为什么刺耳**：同一份文件的名字她要**听两遍**；而且名字里那串**没有语义的记号**被逐字念：

```
"_"                    念 1.7 秒   ← 一个下划线比 5 个中文字（挑出华东区，2.2 秒）还慢
".xlsx"                念 2.3 秒
"-1"                   念 1.4 秒
「结果 挑出华东区 1」     念 2.9 秒   ← 下划线换成空格，同样内容快近一半
对照：同样意思的纯中文「打开第一份华东区的表格文件」(13 字) 念 3.6 秒
```

一行 12.3 秒 × 12 行 ≈ **2.5 分钟**，只为听清"哪一行是哪份表"。

### ③ 确认页：同一句标题既当 1 级标题、又当 2 级标题 → **12.6 秒**

```
标题（第1级）：把这段时间做的事写成一份总结，文字   念 6.3 秒
标题（第2级）：把这段时间做的事写成一份总结，文字   念 6.3 秒
```

**为什么刺耳**：这不是"念两遍"的假象（§3 已撤那条）—— 它是**两个真的标题节点**
（`ControlView` 里各一个，一个 `heading=1`、一个 `heading=2`），意思是页面把**同一个标题**
在页头和确认卡里各放了一次、并都标成了标题。读屏用户按标题跳时会**撞见两个一模一样的标题**，
听完 **12.6 秒**才发现是同一句。
（**范围声明**：这一条只有 UIA 证据，**没有 ETW 实证** —— 我们两边都没对确认页抓过 ETW，§5 第 4 条。）

> **陪跑一条（不算进 3 条）**：结果面板那句标题被读成
> `退出列表, 标题级别 2 我做的结果 你做过的东西都在这里，最近的在最上面。`（**7.8 秒**）——
> 一句里混了**操作词**（退出列表）、**技术词**（"标题级别 2"）和标题正文。这条有 ETW 实证
> （另一条分支的 `results.xml` 里确实有这句）。"标题级别 2"这类词对王姐**没有意义**。

## 5. 我没能验证什么（如实列，不写成「通过」）

1. **"真的出声、她听到的声音"没验** ✗ —— **本轮最大的边界**。这台机器 `Win32_SoundDevice = 0`。
   我验的是「**读屏会念成哪些字**」（UIA 的 `ControlType` + `Name`），**不是**「她戴耳机听完
   觉得好不好」。语速、停顿、重音、念错字、中文会不会变成乱码 —— **一条都没验**。
2. **没能给 Narrator 下命令** ✗ —— 无命令行、窗口无可读节点、单例、且杀不掉（§1.2/§1.3）。
   所以"让它照着清单念一遍"这条**做不到**。
3. **"Narrator 为什么杀不掉 / 那次崩溃为什么"** ✗ —— 我**没能复现那次崩溃**（§1.4），
   也没查到崩溃根因。只如实记它在案。
4. **确认页没有 ETW 实证** ✗ —— §4③ 的"同一标题 1 级又 2 级"只有 **UIA（ControlView）** 证据；
   我们两条分支都**没对确认页抓 ETW**。要把它升到"读屏嘴里确认"的硬度，得补一次确认页的 ETW。
5. **`RawView` / `ControlView` / `ContentView` 之外，读屏到底还叠加了什么** ✗ ——
   我按 `ControlView` 算，并证明 `RawView` 会高估；但读屏还有**实时区域、输入法、扫描状态**等
   动态事件（另一条分支的 ETW 里抓到了「扫描」「英语输入模式」这类噪音）。
   这些**不是我这一层能算的** —— 我这层给的是**静态树**。
6. **只有 WebView2 这一种宿主** ✗ —— UIA 树是 WebView2 暴露的；换宿主
   （macOS WKWebView / 将来换运行时）树可能完全不同，**没验**。
7. **每场只跑了 1～2 轮** ✗ —— `home` / `confirm` / `results` 各 1 轮有效（在当前 `829f2e3` 的构建上），
   加上早期 1 轮作废（首轮 `results` 面板是空的，因为另一场把夹具清了）。
   没有做到"各 3 次结论一致"。
8. **`ListItem` 名字过长要不要改** ✗ —— 12 行的 `ListItem` 名字是**整行 101 字**。
   我**没有**把它算进"刺耳 3 条"，因为 `ListItem` **不可 Tab**、键盘走不到（§3）；
   但**读屏还有别的导航方式**（"下一个列表项"），走那条会不会念它，**我没验**。
   要不要给 `ListItem` 一个短名字，是**产品决定**。
