# 评审流水线：为什么"我来评审"会变成瓶颈，以及怎么绕开

## 问题（有实测）

一个 agent 一小时能写完的东西，我读完 + 核对 + 跑门禁要 15–30 分钟 ✗ ——**多开 agent 只会让排队变长**，
不会让合并变快。这就是"并行度已经够了，瓶颈在我的评审带宽"的意思 ✓。

## 做法：作者 → **独立评审** → 修 → 集成

```
brief（自足、含验收标准）
   ↓
作者 agent → 提交 → push → 开 PR
   ↓
评审 agent（独立 worktree、**不许改代码**）→ 评审报告（逐条结论 + 证据 + 最小修法）
   ↓
   ├── 没问题 → 集成者（我）只做最终裁决：合并 ✓
   └── 有问题 → 修 bug agent（把评审原文原样给它）→ 评审报告里的"必修"逐条修
                ↓
             集成者复核"每条必修都有证据" → 合并 ✓
```

## 评审 agent 的 brief 骨架（可直接复用）

必须写进去的六条（**少一条就会退化成"客气地点头"** ✗）：

1. **"你的任务是尽力挑出问题，不是复述 PR 描述"** ✓ —— 一句话定调，比任何细则都有效；
2. **逐条核对 PR 描述里的断言**：描述说"点一下就填进输入框" → 去测试里看是**断言了这件事** ✓
   还是只"存在一个测试" ✗；描述说"三句话都在" → `grep` 原文 ✓；
3. **跑门禁并贴原始输出**（e2e + dom-smoke ✓），不写"跑过了没问题" ✗；
4. **找"看起来对但没接上"的地方** —— 这是评审最值钱的部分 ✓（例：例子点击改了本地变量但没接到
   真正的提交路径 ✗）；并且要求它**写清自己怎么验的**（读了哪个文件、跑了什么）✓；
5. **结论必须落到 `文件:行` + 最小修法**（一两句 ✓），并给"可以合并 / 有 N 处要改"的明确判断 ✓；
6. **纪律**：不许改任何代码 ✗；**没验的就说没验** ✗，不许写"看起来没问题" ✓。

再补一条**只有评审能发现的东西**：**对照基线** —— 评一个改动时，问"这个是它引入的，还是原来就有？"
✓（实测靠这一条抓到过一个"新引入的布局回归" ✓✓）。

## 实测效果（第一次用）

对 PR #133（693 行、6 个文件）的独立评审：

- 抓到 **3 处必修**：① 向导最后一步在 800×560 下**有 116px 永远滚不到** ✗（而且是**这个 PR 新引入的**，
  靠"对照基线"发现 ✓）；② 我挑的那句"她想不到可以这样做"的例子**在它被接进的那条路上走不通** ✗
  （填进框 → 落到要选文件的页面 → 卡住；它追了 4 个文件给出三处一致的证据 ✓）；③ 第一次做成后的提示
  对"点卡片"的场景说"刚才那句话" ✗；
- 另给 **4 条建议**，其中一条指出**这个 PR 的核心声明没有回归保护** ✗（`dom-smoke` 没点例子、没读输入框 ✓）；
- **并如实写了自己没验的**（没在 Windows 真机上验过 ✓；有一处结论是读代码得出的、不是真机复现 ✓）。

报告 ~7500 字，**用时约 10 分钟**，比我逐行读 693 行更快、而且抓到了我会漏的东西 ✓。

## 什么时候**不要**用

- 纯文档 / 版本号 / 依赖升级这类**没有行为声明**的 PR ✗（没有断言可核对 ✓，评审会退化成读一遍 ✓）；
- 评审对象还没有"能跑的验证"时 ✗ —— 先让作者把门禁跑通再评 ✓，否则评审在替作者做他的活 ✓。

## 谁修？（分工）

评审**只报告** ✓；修由**另一个** agent 做（把评审原文原样给它 ✓，并要求它写"哪些结论我确认、
哪些我不同意 ✗ —— 评审也会错 ✓"）。这样"发现"和"修改"分开，避免作者顺手把问题解释掉 ✗。
