# 撤销的边界：能撤什么、撤几次、多久、撤不回来时她看到什么

问题来自她真正的恐惧：**过两天发现做错了，还能不能撤回来。**
这篇只回答"现在代码里到底是怎么做的"，**不写我们希望它怎么做**。每一行都给出依据
（文件:行 / 哪个测试）；核不出来的，单列一节写"没核出来 + 为什么" ✓。

结论先放前面：**撤销在时间上不过期**（重启后还在 ✓），但**不是无限的**——
它受"备份的体积/数量上限"和"运行记录只留 200 条"两条边界夹着；而后一条一旦越过，
撤销会**什么都不做却报告成功**（下面第 3 节，这条最危险）。

## 2. 撤不回来时，具体会说什么

Rust 的 `undo_files` 其实算了**逐条的、带文件夹名**的原因；但到界面之前**被丢掉了**
（界面只拿到"几个"。这一节先列 Rust 会说什么，再列她实际看到什么——两者不一样）。

`undo_files`（`gui/src-tauri/src/files.rs:350-402`）对每个失败的路径产出：

| 现场 | Rust 的原话（`files.rs`） | 行 |
| --- | --- | --- |
| 本次新建的文件已经不在了 | `<路径>（已经不在这里了，可能已被你或别的程序移走）` | `:364` |
| 移走失败 | `<路径>（没能移走：<错误>；文件还在原处）` | `:372` |
| 被改/被删的文件没有可用备份 | `<路径>（没有可用的备份，无法自动还原；可以到 <文件夹> 文件夹里找找）` | `:380` |
| 备份文件本身丢了 | `<路径>（备份文件丢了；可以到 <文件夹> 文件夹里找找）` | `:388` |
| 还原时复制失败 | `<路径>（没能还原：<错误>）` | `:395` |

**到界面时只剩个数**：`store.undoRun` 只取 `restored.length` 和 `failed.length` 写进提示
（`gui/src/store.ts:1448-1463`）；历史列表也只渲染 `run.failed?.length`
（`gui/src/simple/History.tsx:174-176` → `gui/src/simple/copy-history.ts:64-65`：
`有 N 个文件没能自动还原，请按提示去文件夹里看看。`）。
也就是说，Rust 算出的、**带具体 `<文件夹>` 名**的那几条，没有任何一处界面显示出来
（已全仓 grep `run.failed` / `failedFiles` 核过）。**她看到的最具体的话只有
`没能自动放回去的那几个，需要你打开文件所在的文件夹，把它们放回原来的地方。`
（`copy-notice.ts:53-54`）——说了"打开文件夹"，但没说是哪一个。**

### 2.1 撤销依赖的是两份东西，不只备份

`undo_run` 需要**两份**：
1. `<run>/before.json`（备份映射）—— `files.rs:695`；
2. **运行记录里的** `undo.{created,modified,deleted}` —— `files.rs:699-706`。

第 2 份存在 `runs.json` 里（前端写入见 `gui/src/store.ts:1218-1231`）。所以：
**备份文件还在，也不代表还能撤**——只要运行记录被 200 条上限挤掉，就不行了。

## 3. 最该知道的一条边界：记录被挤掉后，撤销会"静悄悄什么都不做"

`undo_run` 找不到那条记录时，`created/modified/deleted` 全为空 → `undo_files` 无事可做
→ 返回 `{restored: [], failed: []}`，且**不写任何东西**（`files.rs:699-723`）。

前端拿到 `failed.length === 0`，于是走"成功"那条：
`已经放回去了：0 个文件恢复原样。`（`gui/src/store.ts:1453-1455`）。

**即：运行记录不在磁盘上时，点"撤销"看起来是成功的，其实一个文件都没动。**
对"怕弄坏东西"的她，这是最坏的一种失败——**报告成功，却什么也没做**。

依据：`gui/src-tauri/src/files.rs:699-706`（按记录取动作，取不到就是空）、
`:1453-1455`（前端按"没有失败"判成功）。

**触发条件（我按代码路径推的）**：正常情况下，界面里显示的记录都来自磁盘
（两边都截断到 200 条：`files.rs:478` 与 `store.ts:1228`；启动/每次撤销后都重读
`store.ts:502`、`:1460`），所以**记录总在，这条走不到**。但有一条真实可达的路：
`save_run` 写盘失败时，前端把记录留在**内存**里继续显示
（`store.ts:1231-1234` 的 catch）——**这一次运行内**它就在历史里，点"撤销"却会在
Rust 侧找不到记录 → 报"已经放回去了：0 个文件恢复原样。"。
**注意：这条我只按代码路径推，没有在真机复现**（原因见第 5 节）。

## 4. 另一条"名不副实"：注释说"撤销本身也可撤销"，但没有这条路

`files.rs` 的注释写：把本次新建的文件移进 `removed/`，"kept so the undo itself is
undoable"（`:40-41`、`:347`）。

事实是：`removed/` **只有写、没有读**——Rust 侧除 `undo_files` 自己写入外无任何代码读它，
也没有任何 IPC 命令能把它恢复回去（`files.rs` 的 `#[tauri::command]` 共 10 个，见 `:573-691`，
没有一个是"撤销撤销"）。唯一的"读者"是测试（`gui/src-tauri/tests/files.rs:212-216`）。

所以："撤销本身可撤销"目前是**实现了一半的承诺**（文件留着，但没有界面路径去用）。
真要在界面上兑现，属于改 Rust + 加界面，见第 5 节。

## 6. 为什么这轮**不改文案**（任务允许的另一个选择）

任务说："如果现有一句话是错的或会误导，改它；如果没错，就只交文档。"
我把 `copy-notice.ts` 与 `copy-recovery.ts` 逐句对了一遍，结论是**不改**，理由要分开说：

1. **`copy-recovery.ts` 里根本没有一句关于撤销的话** —— 它管的是"出错后按哪个按钮"，
   与撤销无关（已逐句核过）。改它反而会污染它的范围。
2. **能误导的那几句，根因是行为而不是措辞**，改文案会让情况更糟或掩盖问题：
   - `已经放回去了：N 个文件恢复原样。`（`store.ts:1454`）在 `N=0` 时是错的，
     但 `N` 是**动态值**，`copy-notice.ts` 里的 `undoOkHow` 是**静态句**，拿不到它；
     要诚实地把"0 个"说圆，得先修行为（把"无记录"与"真撤了 0 个能区分开）—— 那是 `files.rs`/`store.ts`，
     本轮硬约束不改 ✗。
   - `undoOkHow`（`文件已经恢复成动手前的样子……`，`copy-notice.ts:51`）在**正常路径上是对的**，
     只有当上面那个 bug 触发时才名不副实。把它改得含含糊糊（例如加"如果真放回去了的话"）
     会让**绝大多数正常成功**的那一句变差 ✗ —— 这是拿措辞去补行为漏洞，双重代价。
   - "请按提示去文件夹里看看"里没有提示（第 2 节）：缺的是"把逐条原因显示出来"这个**能力**，
     不是某句措辞；补它要动 `store.ts`/`History.tsx`/`copy-history.ts`，都不在本轮可改文件里 ✗。
3. **她真正的恐惧是"过两天还能不能撤"** —— 对这个问题，代码给出的答案是"能（不限天数、重启也在）"，
   而现成文案里没有任何一句说反了它（`copy-first-run.ts:125` 的"做过的事还能撤回来"与事实一致）。
   所以不存在"现成句子说错了、只需改一个词"这种便宜事 ✗。

一句话：**这轮只交文档**，并把上面那几条越界项点名，留给能改 Rust / store / History 的那一轮。
